# Weather API (Java / Spring Boot)

Drop-in replacement for the Node API in `../server`. It serves the same `/api/v1` routes, request and
response shapes, status codes, error codes and auth behaviour, against the same PostgreSQL database.
The frontend needs no code changes; only its `VITE_API_URL` would point here after cutover.

See [MIGRATION.md](MIGRATION.md) for the feature inventory, endpoint compatibility table and the
list of intentional behaviour differences.

## Stack

- Java 21, Spring Boot 4.1 (Web MVC, Security, Data JPA, Validation, Actuator), virtual threads
- PostgreSQL + Flyway (the Prisma schema is baselined, never regenerated by Hibernate: `ddl-auto: none`)
- JWT (HS256, Nimbus) with rotating refresh tokens in an `httpOnly` cookie, bcrypt (compatible with existing bcryptjs hashes)
- JDK `HttpClient` with connect/read timeouts and Caffeine caches for Visual Crossing / Open-Meteo / Nominatim
- JUnit 5 + Testcontainers (real PostgreSQL) for integration tests

## Layout

```
src/main/java/com/weather
  config/        env binding, DataSource (accepts Prisma-style DATABASE_URL), security, CORS, Jackson, filters
  controller/    REST controllers, zod-compatible query/body validation
  service/       business logic (auth, settings, favorites, search history, notifications, weather, locations)
  repository/    Spring Data JPA repositories
  entity/        JPA entities mapped onto the existing Prisma tables
  dto/           request/response records
  mapper/        entity -> JSON and provider -> API mappers (weather, alerts, air quality)
  security/      JWT, auth filter, bcryptjs-compatible encoder
  exception/     ApiException + global error handler producing {"error":{code,message,details,requestId}}
  integration/   Visual Crossing, Open-Meteo (forecast, geocoding, air quality), Nominatim clients
src/main/resources
  application.yml
  db/migration/V1__baseline_prisma_schema.sql
```

There is no `scheduler` package: the Node API has no scheduled jobs (alert sync runs on request via
`POST /api/v1/notifications/me/sync`), so none were added.

## Environment variables

Same names as the Node API, so existing hosting config carries over. See `.env.example`.

| Variable | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | yes | `postgresql://user:pass@host:port/db?sslmode=require` (Prisma format accepted) |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | yes | min 32 chars; must equal the Node values to keep existing sessions valid |
| `CORS_ORIGINS` | yes in production | comma-separated, must include the Vercel frontend origin |
| `NODE_ENV` | no | `production` enables `Secure; SameSite=None` refresh cookie |
| `PORT` | no | default 4000, binds `0.0.0.0` |
| `JWT_ACCESS_EXPIRES_IN` / `JWT_REFRESH_EXPIRES_IN` | no | `15m` / `7d` |
| `REFRESH_COOKIE_NAME`, `BCRYPT_SALT_ROUNDS`, `LOG_LEVEL`, `DB_POOL_SIZE` | no | |
| `VISUAL_CROSSING_API_KEY` | no | without it, Open-Meteo is used (same fallback as Node) |
| `OPENWEATHER_API_KEY` | no | enables map tile overlays |
| `UPSTREAM_CONNECT_TIMEOUT`, `UPSTREAM_READ_TIMEOUT`, `WEATHER_CACHE_TTL`, `GEOCODING_CACHE_TTL` | no | `4s`, `8s`, `5m`, `6h` |
| `RATE_LIMIT_AUTH_PER_MINUTE`, `RATE_LIMIT_PUBLIC_PER_MINUTE` | no | per client IP: login/register `10`, public weather/location routes `300`; `0` disables. In-memory, so per instance |

## Public vs. authenticated routes

Weather (`/weather/**`), locations (`/locations/**`), health and login/register/refresh/logout are public.
A missing, invalid or expired token on a public route is ignored, never a 401. Profile, settings,
favorites, search history, notifications and users require a valid access token (401 otherwise), and
every record is checked against its owner server-side (403/404 for someone else's data).

API keys are only used server-side; they are never returned to the client (the OpenWeather key is
embedded only in the tile URL template, exactly as the Node API did).

## Running locally

No local JDK/Maven is required; everything can run through Docker.

```powershell
# PostgreSQL (the existing compose file in ../server works too)
docker run -d --name weather-db -e POSTGRES_USER=weather -e POSTGRES_PASSWORD=weather -e POSTGRES_DB=weather -p 5432:5432 postgres:17-alpine

# Build and run the image
docker build -t weather-api-java backend
docker run --rm -p 4000:4000 `
  -e DATABASE_URL=postgresql://weather:weather@host.docker.internal:5432/weather `
  -e JWT_ACCESS_SECRET=<32+ chars> -e JWT_REFRESH_SECRET=<32+ chars> `
  -e CORS_ORIGINS=http://localhost:5173 weather-api-java

curl http://localhost:4000/api/v1/health
```

With a local JDK 21 + Maven: `mvn spring-boot:run` (env vars as above) or `mvn package && java -jar target/weather-api-*.jar`.

On first start against an empty database Flyway creates the schema from V1. Against the existing
(Prisma-managed) database it records a baseline at version 1 and changes nothing.

## Tests

```powershell
# Needs Docker (Testcontainers starts postgres:17-alpine)
mvn test

# Or entirely in Docker (Windows host):
docker run --rm -v "${PWD}\backend:/workspace" -v weather-m2:/root/.m2 -w /workspace `
  -v //var/run/docker.sock:/var/run/docker.sock `
  -e TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal -e TESTCONTAINERS_RYUK_DISABLED=true `
  maven:3.9-eclipse-temurin-21 mvn -B test
```

47 tests: auth flows and cookies, per-user data (settings, favorites, history, notifications),
weather/locations/air quality against stubbed upstreams, a legacy-database test that loads the real
Prisma migrations plus Node-created rows/tokens/bcryptjs hashes and verifies the Java API accepts them,
and unit tests for JWT, password hashing, unit conversion and air-quality classification.

## Deployment (Render, Docker)

The frontend stays on Vercel. The Java API is deployed as a **new, separate** service; the current
Node API keeps running until the Java one is verified.

1. Render dashboard: New > Blueprint, pick this repo, blueprint path `backend/render.yaml`
   (or New > Web Service, runtime Docker, root directory `backend`, health check `/api/v1/health`).
2. Set the secret env vars: `DATABASE_URL` (the same Neon database), `JWT_ACCESS_SECRET` and
   `JWT_REFRESH_SECRET` (same values as the Node API), `CORS_ORIGINS=https://weather-lac-six.vercel.app`,
   and optionally `VISUAL_CROSSING_API_KEY` / `OPENWEATHER_API_KEY`.
3. Verify the new URL: `/api/v1/health`, then `node scripts/smoke.mjs https://<new-host>/api/v1`
   (it registers one throwaway `smoke<timestamp>@example.com` account), or point a Vercel preview of
   the frontend at it.
4. Cutover (needs approval): change `VITE_API_URL` in the Vercel frontend project and redeploy.
   Rollback is changing it back; the database is shared and untouched.
5. Only after a verification period, retire the Node API.

Render free instances sleep after 15 minutes idle; the first request after that takes ~30 s
(JVM start ~6 s plus container start).
